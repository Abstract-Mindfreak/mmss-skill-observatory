## Рекомендуемый вариант

Создать один понятный рабочий путь **«Исследование»** поверх существующих данных и API: человек выбирает инструкцию и область, задаёт ограничения и запускает кампанию явно; затем видит ход по областям, блокировки и результаты, рассматривает доказательства и отдельно решает, принять ли вывод или разрешить правку. Это адаптация существующего S2, не новая исследовательская модель и не автоматический запуск.

### Основной маршрут

1. Открыть проект и активную версию: название, hash/обновление, статус индекса и короткая сводка без внутреннего JSON.
2. Выбрать область по разделу/положению через фильтрованный ограниченный список; показать выбранный scope и основания.
3. Установить глубину, бюджет, retry/concurrency и условия остановки. Показать роли, существующие назначения и отдельный embedding; перед стартом — preview объёма и материала.
4. Явно нажать «Запустить исследование». До старта только чтение/preview; запуск создаёт campaign/actions и требует видимого подтверждения эффекта.
5. На экране выполнения раздельно показать: состояние кампании, обязательные проверки, машинное заключение, пользовательское решение. Остановку, исчерпание бюджета и незавершённые элементы не сводить к «готово».
6. Открыть вероятную проблему: краткая суть → источник → выполненная проверка → подтверждение/возражение → ограничение → возможные действия. Принятие вывода, редактирование инструкции и повторная проверка — раздельные действия.
7. Вернуться к списку/поиску, сохранив query, фильтр, выбранную версию и адресуемую запись.

## Предлагаемые заметки о ходе исследования

Необязательный opt-in блок объединяет представление событийного журнала (фактически запущено/завершено/приостановлено) и коротких объясняющих заметок о применении политики/выборе следующего действия, но визуально различает их тип. Источники — уже существующие campaign/action/Run/Evaluator/relation события; UI не запрашивает новые длинные объяснения и не требует новых LLM-вызовов. Модельное объяснение, если оно уже сохранено, подписывается как текст модели, не как истинный внутренний ход мыслей. Заметки привязываются к шагу, Run или решению, фильтруются, показывают раскрываемые основания, выключены по умолчанию и попадают в экспорт лишь по opt-in. Хранение новых объяснений не требуется для базовой версии; если появится требование сохранять их отдельно, это отдельный объём/решение по схеме.

## Переиспользование и изменения

**Переиспользовать:** текущий project/version selector; `ResearchCampaignPanel`; campaign policy/actions/items; Semantic Atlas/Search/Position/Relation/Observation; Scenario/Run/Evaluator; Connections/role assignments; export/handoff/Archive; существующие ссылки на source fragments и текущий порт.

**Нужно адаптировать:** навигацию и первый экран; разнести настройку запуска, наблюдение и рассмотрение; нормализовать отображение статусов кампании vs элементов; прогрессивное раскрытие; показать requested model и actual provider/model отдельно; явные пустые/ошибочные/частичные состояния; возврат с сохранением контекста.

**Новые API:** в этой спецификации существующие API достаточны для read/display, включая `GET /api/research-campaign`, `GET /api/semantic/research-state`, handoff/export. Перед этапом 2 нужно проверить существующие методы мутации кампаний и их идемпотентность. Если текущий API не поддерживает раздельное «pause/resume/cancel», использовать имеющийся контракт или предложить его изменение отдельно; этот документ не объявляет новые endpoint существующими.

## Приоритет, риски и решения

**Обязательное для этапа 2:** исследовательский home; явное scope/policy preview; запуск только по нажатию; видимые progress/paused/quota/error/completed states; раздельные campaign/check/conclusion/user decision; источник и ограничения у результата; requested/actual provider/model; сохранение query/filters/back route; техническое состояние в расширенной диагностике; клавиатурный доступ; без побочных записей при открытии.

**Опционально:** opt-in заметки; компактные метрики; персональные фильтры списков.

**Отложено:** автоматические решения/автопринятие; массовое редактирование инструкции; новый движок рекомендаций; миграция схемы ради заметок; новые модельные объяснения; полная замена существующего Atlas/Behavior Lab.

Риски: попытка спрятать ошибки в простом режиме; неверная семантика `completed`; дублирование campaign execution APIs; повреждение связи source/run при переносе панелей; потеря фильтров при навигации; длинные списки и узкий экран; stale/partial API. План отката этапа 2 — feature flag или сохранение старого маршрута до приёмки; не выполнять миграции/массовые изменения данных без отдельного обоснования.

**На согласование:** (1) оставить «Исследование» центральной точкой входа и подчинить ему ручные инструменты; (2) применять обычный/расширенный режим как два уровня детализации без скрытия ошибок; (3) включать заметки только opt-in, без новых LLM-вызовов. Эти решения определяют реальную навигацию и объём этапа 2. Изменение данных, моделей, истории и схемы этим этапом не предлагается.

## План этапа 2

1. Перед кодом перепроверить существующие campaign mutation API и компонентные контракты.
2. Реализовать сначала home, scope/policy preview и явный запуск с read-only initial state.
3. Реализовать progress/result review и разделение четырёх статусов; сохранить ссылки и контекст возврата.
