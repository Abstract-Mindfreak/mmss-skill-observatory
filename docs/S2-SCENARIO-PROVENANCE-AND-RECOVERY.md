## Изменения контракта сценария

Без изменения Prisma-схемы и новых сущностей:

- Explorer получает раздельные значения существующих полей: `objective` — требование из источника; `input` — в том числе гипотетическое тестовое условие; `expectedBehavior` — выведение из требования; `criterion` — наблюдаемое условие оценки. Новые предположения следует обозначать в `limitations`, а не превращать в критерий.
- Описание нового Scenario явно помечает эти четыре значения. Explorer `limitations` сохраняются в ограничениях положения с пометкой, что это гипотезы, а не требования источника.
- Evaluator получает сохранённые поля сценария и тексты связанных с ним исходных Fragment. Он должен отдельно вернуть `criterionBasis` (`supported`, `unsupported` или `unclear`) и verdict. Код принимает CampaignCheck как завершённый только при `criterionBasis=supported` и verdict `pass`/`fail`; отсутствующий или неподдержанный basis оставляет проверку `inconclusive`. Это не требует буквальной цитаты для логического вывода.
- Проверка основания остаётся ограниченной модельной оценкой источников, а не формальным доказательством логического следования. Это ограничение явно сохранено; старые оценки не пересчитаны.

## Retry и восстановление

Распознаются явные timeout, `ETIMEDOUT`, `EAI_AGAIN`, `ECONNRESET`, socket hang-up, connection reset, временная недоступность и HTTP 5xx. Само слово `network`, `socket`, `connection` или `temporarily` больше не делает постоянный отказ временным. Отмена по статусу Run не повторяется, даже если текст ошибки похож на timeout. Квота проверяется отдельно и приостанавливает кампанию без автоматического повторного запроса. Схема сохраняет текст ошибки, но не структурированный provider error code; поэтому retry использует узкий текстовый fallback и доступный статус Run.

Изолированный mock acceptance (`scripts/s2-isolated-research-ui-acceptance.mjs`) подтвердил:

- локализованный FreeLLMAPI timeout допускает последовательную попытку; каждая попытка создаёт отдельное действие и увеличивает счётчик бюджета;
- три timeout-попытки дают attempts 1, 2, 3, использовано 3/3 действия, этап становится `inconclusive`, четвёртая попытка заблокирована;
- quota сохраняет `provider-quota` без автоматической повторной очереди;
- отменённый Run с timeout-похожим текстом не повторяется;
- постоянная ошибка валидации не считается временной (unit regression);
- если сохранённый Run завершился поздно, существующий результат используется без нового action/Run;
- ответ Evaluator с `criterionBasis=unsupported` и даже `verdict=pass` оставляет CampaignCheck и заключение `insufficient-data`;
- все эти проверки использовали mock executor; в fixture создано 0 ModelCall.

### Безопасный preview повтора

Путь для завершённой кампании — **новое исследование**, а не продолжение/открытие старого статуса. `restartResearchCampaign` создаёт отдельную `prepared` кампанию с `predecessorCampaignId` и записью в `processHistory`; исходная запись остаётся completed. Переиспользуются текущие version/hash, scope, policy и снимки назначений ролей. Runs, ModelCalls, сценарии, CampaignChecks и verdict не копируются. Фактический механизм уже проверен ранее изолированным process-center acceptance: restart создаёт новую prepared запись без action и провайдерской работы.

Для данной области full-depth и двух положений обычный проход — 14 действий: на каждое положение Interpreter, Challenger, Explorer, затем по Executor и Evaluator на каждый из двух новых сценариев. Механизм перегенерирует сценарии по исправленному контракту; старые сомнительные сценарии не переиспользуются. Действующий снимок политики содержит лимит 30 и максимум 3 попытки на действие; restart сбрасывает использованный счётчик к нулю, сохраняя предел. 30 покрывает номинальные 14 действий и до 16 дополнительных retry/review действий, но не худший теоретический случай, если все действия исчерпают три попытки. Для верхней границы только базовых 14 действий требуется 42; возможные дополнительные проверки увеличивают её. Кампания не создана и не запущена.

Продолжение `prepared`/допустимой `paused` кампании и retry transient action возможны в пределах текущей незавершённой кампании и её бюджета. Для этой `completed` записи адресного retry Challenger нет; безопасный следующий путь — явное создание нового исследования через «Процессы и очередь» → «Новое исследование с теми же настройками», затем отдельное подтверждение запуска.

## Отображение и ручная проверка

Для завершённой очереди с неуспешным Challenger UI показывает сообщение: **«Очередь завершена. Исследование неполное: Challenger не завершён.»** Под ним выводится сохранённая причина и переход к «Процессы и очередь», где доступно создание нового исследования. Историческая кампания остаётся неизменной.

Браузерная проверка в этом этапе не выполнена: ранее localhost URL policy заблокировала доступ, и повторных попыток/обхода не предпринималось. Ручная проверка пользователем:

1. В Research открыть кампанию `dd2709814cec459aad6fa6b8c4455ad3` и выбрать `6.2.1.1`.
2. Убедиться, что статус очереди `completed`, обязательное взаимодействие `inconclusive`, заключение `insufficient-data`, пользовательский статус положения `proposed`; в уведомлении указаны незавершённый Challenger и timeout.
3. Открыть `Процессы и очередь`, выбрать завершённую кампанию и действие «Новое исследование с теми же настройками». Подтвердить появление отдельной prepared кампании с предшественником, нулевым использованным бюджетом и без скопированных сценариев/Run.
4. Не запускать её без отдельного решения; подготовка не должна отправлять модельный запрос.
